Context: Redblock IGA-to-Downstream Connector Development
About Redblock (the product I work on)

Redblock is an IGA (Identity Governance & Administration) integration platform that acts as a middleware/gateway between upstream identity providers (like SailPoint, Saviynt, Okta Lifecycle Management, Microsoft Entra ID Governance) and downstream applications (Auth0, Active Directory, Salesforce, GitHub, ServiceNow, etc.).

The core value proposition: Upstream IGA tools speak SCIM 2.0 (RFC 7643/7644 standard). Downstream apps each have their own REST APIs with different schemas, auth mechanisms, and quirks. Redblock provides a visual pipeline builder where users construct data flows that:

Receive SCIM requests from IGA tools (Create, Read, Update, Delete, Search, Group/Role membership, Deactivate)
Translate SCIM payloads → downstream app's REST format
Make authenticated API calls to the downstream app
Translate responses back to SCIM format for the IGA tool
Redblock Pipeline Concepts (Redblock-specific UI terminology)

Pipeline structure: DAG of nodes connected by flow edges. Nodes execute in order. Each node has:

Input Variables panel: named references to any ancestor node's output (Key = variable name in script, Value = pill/pointer to source data)
Output: passed downstream

Node types I've worked with:

Start — entry point, holds Pipeline Inputs (user-configurable JSON values)
HTTP Call — makes REST API calls; configured with API Tool (base URL + auth), Path, Method (GET/POST/PATCH/PUT/DELETE), Body, Headers, Query Parameters
Run Script — JavaScript node with Input Variables and a Script (JS) box. Returns an object accessible to downstream nodes.
Condition — branching logic with Condition 0 / Condition 1 outputs
For Loop — iterates over an array; provides loopIndex, iteration, loopItem. Has "Loop" output (per iteration) and "Done" output (after loop finishes)
Cache — persistent key-value storage between pipeline runs
Output / Output1 / Output2 — final data sinks

Key Redblock gotchas we discovered:

Input Variables can reference ANY ancestor node in the DAG (not just directly connected ones), but only via the picker
The variable picker only exposes ancestors, not siblings on parallel branches
Complex For Loop outputs sometimes come through Input Variables as JSON strings (require JSON.parse in the script)
Nested drill-downs in the picker (like For Loop → 1 → http_call_XXX → result → response) don't always resolve correctly — sometimes returns empty objects
The HTTP Call node names its output dynamically like http_call_e5159c (with a random suffix)
Inline JSON Body editors handle pills/variables poorly for booleans and nested objects — Run Scripts are more reliable for building bodies
Path fields support pill references for URL segments: e.g. /users/{id_pill}/roles
What We've Built So Far (Auth0 REST connector)

I've been building pipelines for an Auth0 REST connector that translates SCIM → Auth0 Management API. Completed pipelines:

1. Create User Pipeline (SCIM POST /Users → Auth0 POST /api/v2/users)
Start → Run Script (SCIM → Auth0 body translator) → HTTP Call POST → Output
Maps SCIM emails[primary].value → email, name.givenName → given_name, enterprise extension → app_metadata, etc.
2. Update User Pipeline (SCIM PATCH /Users/{id} → Auth0 PATCH /api/v2/users/{id})
Uses PATCH method with partial body
Handles SCIM active: false → Auth0 blocked: true
Cannot update email + password in same call (Auth0 constraint)
3. Deactivate/Activate Pipelines
Just PATCH /users/{id} with hardcoded {"blocked": true} or {"blocked": false} body
No pipeline inputs needed besides id
Also includes optional Invalidate Sessions call: DELETE /users/{id}/sessions
4. Delete User Pipeline
DELETE /users/{id} — hard delete (irreversible)
5. Entitlement Assignment (add role to user)
POST /users/{id}/roles with body {"roles": ["rol_id"]}
Auth0 role IDs look like rol_abc123xyz456
6. Entitlement Revoke (remove role from user)
DELETE /users/{id}/roles with same body structure as Assign
7. Account Aggregation (currently in progress)
Goal: fetch all users + their assigned roles → return enriched user list
Approach: GET /users → GET /roles → For Loop iterating roles → GET /roles/{role_id}/users per iteration → merge results
Current struggle: extracting per-iteration data from the For Loop's aggregated output. The output is a flat array of {statusCode, statusText, response: [users]} objects, but pill references keep returning empty/undefined. Working through this now.
Auth0-Specific Learnings
Auth0 Management API base: https://{tenant}.us.auth0.com/api/v2
User IDs format: auth0|abc123...
Roles endpoint returns [{id, name, description, type}]
blocked: false is omitted from GET responses (Auth0 quirk)
Password requires: 8+ chars, mixed case, numbers, special chars
user_metadata (user-editable) vs app_metadata (admin-only) — used to store SCIM externalId and enterprise extensions
Roles and Permissions are separate resources (require additional API calls)

OU is a drawer. Domain is an office. DC is the clerk at that office. Forest is the company. GC is the lobby directory covering every office.  Two of those deserve a second sentence, because they are the ones people get wrong.  An OU is only filing. Moving someone between drawers changes nothing about who they are or what they can reach. It is a folder on a laptop, not a security boundary. People routinely assume otherwise.  A forest is the boundary that counts. Not the domain. Microsoft's own guidance is that if you want genuine separation between two parts of a business, you use two forests. This is why your client has five of them, and why so much of the work turned out to be about what does and does not cross that line.  02 How to read an address Every entry has one full address. Learn to read it and most of LDAP stops looking cryptic.  It is written narrowest-first, like naming a person before the street before the city. AD calls it the distinguished name, or DN.  CN=Jane Doe OU=Finance DC=corp DC=local the person the drawer one office: corp.local each step to the left sits inside the one to its right one person the whole office A domain name is split across one DC= part per dot, so corp.local becomes DC=corp,DC=local and ihgint.global becomes DC=ihgint,DC=global. DC here means domain component, which is an unrelated use of the same two letters as domain controller. Blame 1990s naming. When you searched in the pipeline, the Search Base was just the address you started from and Scope was how deep to go. Start at the office and search the subtree, and you sweep everything. Start at one drawer, and you see only that drawer.  03 Your lab, in those terms Three servers, two companies, and five possible connections. Here is why that number is five rather than three.  The thing that surprises everyone: one server answers as two different things depending on which door you knock on. Ask dc01 on one port and it replies as the Finance office clerk — full files, and it will accept changes. Ask the same machine on a different port and it replies as the lobby directory — every office, summaries only, and it will not accept changes. Those port numbers are not a lab invention. 636 and 3269 are the numbers Microsoft assigns everywhere. The oddities — 1636, 2269 — are our proxy putting the other servers on spare doors, which turned out to be genuinely useful for finding a bug.  04 Why anyone pays for this Two expensive problems, and both of them live in the directory.  Nobody can answer "who has access to what" An auditor asks a company to prove that only current employees can reach the finance system. With tens of thousands of accounts spread across five forests, answering by hand is a project, not a query — and the answer is stale before it is finished.  That is aggregation: read every account and every group membership, continuously, so the question becomes something you run rather than something you staff.  Accounts outlive people Someone resigns on a Friday. Their account very often still works months later, because disabling it depended on a human remembering. It is the most common finding in a security audit and a well-worn route into a company.  That is JML — joiner, mover, leaver — the three moments in someone's employment where their access has to change.  Joiner Mover Leaver Jane starts on Monday. Create the account, file it in the right drawer, add the right groups, set a password. Create User Jane moves to Treasury. Move her drawer, swap her groups — and take the old access away, which is the bit Move User · Modify User Jane resigns. Disable the account in minutes rather than months, then delete it on a schedule. Disable User · Delete User The mover case is the one people forget: granting the new access is easy, removing the old access is what audits actually fail on. Every operation on the node exists to serve one of these three moments, or to read the state they leave behind. That is the entire product in one line. 05 What the node actually does Nine operations. Two shapes of answer. One thing it will refuse to do.  Operation	In plain words	Needs Search Users	list people	either connection Search Groups	list groups	either connection Search Group Members	who is in this group	office clerk only Create User	the joiner	office clerk Modify User	change details	office clerk Move User	change drawer — the mover	office clerk Set Password	set or reset a password	office clerk Disable User	the leaver, step one	office clerk Delete User	the leaver, step two	office clerk Reads give you a table. Why Create User asks for a password An account with no password is one the guard will not let through the door — Active Directory refuses to enable it. And the password has to be handed over as the file is created; you cannot create the person first and give them a password afterwards.  So: give it a password and you get a working account. Leave it blank and you get a real but disabled one, which the node tells you about rather than letting you find out on Monday.  06 Five rules that shaped the code Each of these is a thing Active Directory does that will quietly produce a wrong answer rather than an error. They are the reason the node refuses certain combinations before it does anything at all.  Rule 1 — the lobby directory is read-only  You can read the summary board; you cannot edit it. Every change has to go to the office that actually holds the file. Attempt it and raw AD replies unwilling to perform, which tells you nothing. The node checks first and names the problem instead.  Rule 2 — the summary leaves things out  The lobby board lists everyone, but only some details about each of them. Ask it for a detail it does not carry — when an account expires, say — and you get a blank, not an error. A blank expiry date reads exactly like "never expires", which is how you end up leaving an account open.  Which details are missing differs per company, so the node reads the list from the directory itself and warns you by name. In your lab that list is 201 attributes long; at your client it will be a different number, and the code does not care.  Rule 3 — a clerk will point, and the pointer is useless  Ask the corp.local clerk about someone in the amer office and they do not say "not here". They hand you a note saying try amer.corp.local — a referral. A well-behaved LDAP client dutifully tries to phone that address, which from our network does not exist, and hangs.  The node never follows them. It counts them and tells you which office it was pointed at, so an empty result comes with a reason attached.  Rule 4 — a pass for one company is not a pass for the other  Even with a trust in place, an account from company one could not sign in to company two at all in our tests. And permission to create people is granted office by office regardless.  So each forest needs its own account with its own permissions. Five forests means five of those conversations with five different administrators — which is usually the slow part of a project like this, not the code.  Rule 5 — the interesting memberships are the invisible ones  When someone from company one is given access in company two, that membership can only be recorded in a particular kind of group — and that kind of group never publishes its membership to any lobby directory.  So the highest-privilege relationships in the estate are precisely the ones a summary-only read will miss. Not with an error — the group simply appears to have nobody in it. Those have to be read from the owning office directly, which is why Search Group Members refuses to run against a lobby directory.  07 Go and look Five things you can do in the pipeline right now, each of which makes one of the rules visible.  One query, two offices Corp GC + Search Users. The results include people from both corp.local and amer.corp.local. One connection, the whole company. The missing detail Same thing, but put accountExpires in Attributes. You get a warning naming it. Switch to Corp DC and the warning goes, because the office clerk holds the full file. That is rule 2, live. A working joiner Corp DC + Create User into OU=Joiners,DC=corp,DC=local, with a password. The receipt comes back with accountEnabled: true. Leave the password blank and it comes back false. The refusal Notice that Corp GC does not even offer the change operations. The node asks the directory what each connection is and hides what it cannot do. The leaver Disable User then Delete User on the account you just made. Two operations, and the whole leaver problem in miniature. The lab exists so all of that can be got wrong somewhere it does not matter. It is a rehearsal stage, not the specification — which is why the code reads facts like the attribute list from whatever directory it is pointed at, rather than remembering what this one happened to say.

## ASSISTANT · 2026-09-08T13:44:39.133739Z

Sure. Using the framing from your doc, but stepping back to first principles:

**Active Directory is a database plus a bouncer.**

The database holds a record for every "thing" in a company's IT world — every employee, every laptop, every printer, every shared folder, every group. All of them are just entries in the same list. A person entry has fields like name, email, job title, password hash. A laptop entry has fields like machine name, OS version, who owns it. Same structure, different fields.

The bouncer is the part that answers two questions all day, every day:

- *"Is this person who they say they are?"* (authentication — checking the password when you log into your work laptop)
- *"Are they allowed to open this thing?"* (authorization — checking whether you can open the finance shared drive)

Every time you log into a work computer, open a shared network folder, print to the office printer, or hit an internal website, something is asking Active Directory those two questions in the background. You don't see it because it's fast and it just works.

**Why it exists.** Before AD, every server and every application had its own user list. A new hire meant creating accounts in fifteen different places. Someone leaving meant remembering to delete them from all fifteen — and someone always forgot. AD centralised that: one account, one password, and every system asks the same authority.

Microsoft shipped it in Windows 2000 and it became the default for basically every corporate network. Even now, twenty-five years later, if you work at a company with more than a few hundred people on Windows, there's almost certainly an AD somewhere underneath deciding what you can touch.

**The shape of it.** Entries are organised into a tree — narrowest thing on the left, broadest on the right, like your `CN=Jane Doe, OU=Finance, DC=corp, DC=local` example. That tree lives on a server called a Domain Controller (DC), which is the "office clerk" in your analogy. Big companies run several DCs so if one goes down the others keep answering, and they replicate changes between themselves.

Zoom out one level: a **domain** is one office with its own clerk. A **forest** is the whole company — one or more domains that trust each other and share the same underlying rulebook. The forest is the real security boundary; the domain isn't, despite what the name suggests. That's the counterintuitive bit your doc keeps hammering, and it's the reason your client having five forests means five genuinely separate worlds that don't automatically see each other.

**What people actually do with it, day to day:**

- Log employees in and out of their machines
- Control who can access which file share, printer, or app
- Push software and security policies to laptops (Group Policy)
- Prove to auditors that access is under control — the "who has access to what" question, which is the aggregation problem your product solves
- Handle the joiner/mover/leaver lifecycle — creating accounts on day one, updating them when people change roles, disabling them within minutes of someone leaving

That last one is where AD becomes a security problem rather than a plumbing problem. An account whose owner left months ago but still works is one of the most common findings in any security audit, and it's a well-worn way for attackers to get in. Which is exactly why an IGA tool wants a reliable pipe into AD to shut those accounts down automatically — and why Redblock is building the pipe.

**One more thing worth knowing.** Modern Microsoft has a second product called **Entra ID** (formerly Azure AD), which is the cloud version. It does similar things — authentication, authorization, group membership — but it's not the same product. It talks HTTP and JSON via Microsoft Graph, whereas classic AD talks LDAP over its own ports. Most large companies now run both: on-prem AD for the traditional Windows stuff, Entra ID for cloud apps and Microsoft 365, with a sync tool bridging them. When someone says "AD" today they might mean either, and the connector shape is completely different for each — which is why the very first question on any AD integration is "which one, or both?"

That's the whole thing at a conceptual level. Anything you want to go deeper on — LDAP mechanics, how authentication actually flows, Group Policy, trusts, replication — say the word.
